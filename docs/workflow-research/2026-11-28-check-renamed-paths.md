# When a documented path moves, look for the command that still uses it

**Proposed — for human review.** Try one author-side check on a rename: after the ordinary diff review, search tracked Markdown for the old path. Fix a match only if someone following a current instruction would now use the wrong location. No extra reviewer step or PR-body field.

**Why Oya:** When [`node/kernel` became `node/production`](https://github.com/oyaprotocol/oya-commitments/commit/594a6e2471b8a7b2add9094a8fe36402ea4a71fd), a reader starting in `contracts/README.md` needed a new `npm --prefix` argument as well as a new link. The commit updated both. This is a good example to preserve, not a report of a broken guide. A link checker alone would miss a path inside a shell command. Unlike [#253](https://github.com/oyaprotocol/oya-commitments/pull/253), the goal here is to correct instructions *before* review, not guide reviewers through the implementation.

**Why check, not replace:** In [*When Instruction Files Go Stale: Documentation Debt and Hidden Cost in Coding Agents*](https://arxiv.org/html/2611.09802v1) (Tural Mehtiyev, Biruk Tadesse, Lawrence Arkoh and Wesley Assunção, November 6, 2026, preprint, §IV), two models worked on 22 maintenance tasks under stale, corrected and removed instructions. In one case, 19 of 40 Sonnet runs with a stale test command first checked their fix without running any tests, versus none of 40 with the correction. Final fixes usually succeeded either way. Three instruction-file cases cannot tell us how often Oya's operator guides go stale or how much reviewer time a check would save.

Wen Siang Tan, Markus Wagner and Christoph Treude's [*Detecting outdated code element references in software repository documentation*](https://link.springer.com/article/10.1007/s10664-023-10397-6) (published November 21, 2023, RQ4) gives a reason not to turn a match into a ticket: of 15 projects contacted, four responded positively, four reported false positives and seven did not respond. A removed flag, for example, was still useful to some installers. A migration note naming the old directory is not a broken command.

**Proposed pilot (not run):** On the next three agent-authored changes that move a documented file or directory, finish the normal author review first. Then run a literal search such as `git grep -n -F 'node/kernel' -- '*.md'` with the path actually moved. Read each hit in context. For a current command, check its path from the guide's stated working directory against the proposed tree. Leave history and compatibility examples alone. A literal search can miss a relative or abbreviated path, so an empty result is not proof that every guide works.

Use the draft immediately before the search as the baseline. The author privately notes elapsed time, still-broken instructions found beyond ordinary review, and any unnecessary edits called out in normal review. Do not ask the reviewer to score the trial. Keep the check only if it catches a concrete missed instruction with little extra author effort and no needless review churn. Stop after three eligible changes if it finds none, or sooner if sorting irrelevant hits costs more than checking the affected guide directly. Ending the pilot means omitting the search; there is no scanner or policy to remove.
